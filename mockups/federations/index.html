Federations — UI/UX mockup

aMap view bRenewal prompt cJoin request dRoster & win-tracker eEvents panel

Federations are fluid, opt-in blocs built almost entirely on the existing bilateral alliance system — no new request/accept UI. Two allies who complete their first renewal found one automatically; anyone else joins by getting sponsored, then having every current member independently accept a tagged alliance request. Below: five screens covering founding, joining, the live map/roster/win-tracker state, and a fracture event, styled against OpenFront's existing dark HUD components.

Relationship treatment

No relation — default 1px border
Bilateral ally — thin slate border, own territory only
Federation member — glowing accent border + tinted zone + crest
Design rationale Each nation keeps its own persistent identity color — the same one used in chat, the player list, and everywhere else — because federations are fluid and recoloring a territory on every join/prune would fight the player's established identity mid-game. Instead, federation membership is layered on top: SamRadiusPass already merges overlapping ally SAM-range circles into one outline via AllianceClusters' union-find, exactly the same "many owners, one visible boundary" trick this reuses for territory borders — a continuous glowing outline in the federation's accent color, a faint tinted backing zone, and one crest per cluster. A plain bilateral ally that isn't federated gets a much quieter signal: its own thin slate-colored border and, where relevant, a dotted tether line — never the glow, the zone, or a crest. That gap in intensity is the whole answer to "same federation" vs "just allied."

Design rationale This is the entire "founding" UI: one banner injected above the existing RENEW_ALLIANCE actionable-event card, shown exactly once — the first time two allies renew. It sits inside the same bg-gray-800/92 … border-l-4 border-yellow-400 card the game already renders, uses the federation's own accent color so it doesn't compete with the card's existing warn-yellow border, and disappears for every renewal after. No new modal, no separate confirmation step — the existing Renew alliance button does double duty.

Why segmented, not blended

Victory credit is proportional to contributed territory, not split evenly — a single merged bar would hide that Kestrel is carrying nearly half the coalition. Each member gets its own segment, sized to its share, in its own identity color, so contribution reads at the same glance as the total.

Design rationale Reuses the exact segmented-bar technique already in ControlPanel's troop meter (absolute inset-y-0 … transform: translateX(x%) scaleX(y) stacking) — extended from two segments (owned/attacking) to N segments, one per member, each in that member's own persistent color so the meter and the roster list read as the same information at two zoom levels.

Combined territory drops from 32.4% to 26.5% the instant the link breaks — Ostwind's segment simply disappears from the stack.

Design rationale Three plain rows in the same feed, nothing modal: the federation's own history (founding, a join) sits in the low-key scrolling log exactly like any other background event; the alliance expiry keeps its existing unmodified warn-yellow treatment; the prune is a new but equally quiet entry, colored with the federation's own accent so it's legible as "this affects your federation" without implying urgency the game doesn't intend. The roster and meter update in the same tick — Ostwind's row and segment simply go away, no separate confirmation.
Mockup only — static HTML matching OpenFront's existing Tailwind tokens, component patterns (ActionableEvents, EventsDisplay, PlayerPanel, ControlPanel's segmented meter) and the AllianceClusters/SamRadiusPass border-union technique. No game logic implemented.
